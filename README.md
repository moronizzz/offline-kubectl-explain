# Offline kubectl explain

`explain.py` prints the same output as `kubectl explain`, without a cluster. It reads a saved
OpenAPI v3 spec from `openapi-v3/`.

> **AI-generated.** The code and docs were written with AI (Claude Code). Output is checked
> against real `kubectl explain` output saved in `golden/` (see below).

```bash
./explain.py deployment.spec.strategy
./explain.py deployment.spec --recursive
./explain.py horizontalpodautoscaler --api-version=autoscaling/v2
```

Requires Python 3.9+, stdlib only.

Output is colored in a terminal and plain when piped, so it still diffs cleanly against kubectl.
Set `NO_COLOR=1` to turn colors off, or pass `--color=always` to keep them through a pager:
`./explain.py pod --recursive --color=always | less -R`.

## Where the spec comes from

| Source | How | Output |
|---|---|---|
| Live server (committed: v1.36.5) | `sudo ./golden.sh` on a throwaway Ubuntu VM, then copy `openapi-v3/` back | Byte-identical to `kubectl explain`, enums included |
| Upstream GitHub files | `./fetch-swagger.sh [tag]` locally, no cluster | Same, minus enum lines: upstream files carry no enum data |

Either way, delete `openapi-v3/` before replacing it, so files from two sources don't mix.

The spec files are generated by Kubernetes and licensed under Apache-2.0, the same as this repo.

## Checking against real kubectl

`golden.sh` also saves real `kubectl explain` outputs to `golden/`. To compare:

```bash
for f in golden/*.txt; do
  n=$(basename "$f" .txt)
  case $n in
    hpa.autoscaling-v2)        args=(horizontalpodautoscaler --api-version=autoscaling/v2) ;;
    deployment.spec.recursive) args=(deployment.spec --recursive) ;;
    *)                         args=("$n") ;;
  esac
  diff -q "$f" <(./explain.py "${args[@]}") >/dev/null && echo "OK   $n" || echo "DIFF $n"
done
```

## Limits

- Kind names only: `deployment` works, `deployments` and `deploy` don't.
- CRDs only if they were in the cluster the spec came from (the committed dump has k3s's own).
- When a kind exists in several groups or versions, it picks core group first, then the most
  stable version. kubectl uses server discovery order instead; pass `--api-version` if they differ.
